# 2. システムアーキテクチャ

## 2.1 論理アーキテクチャ

```text
┌──────────────────────────────────────┐
│              Client                  │
└─────────────────┬────────────────────┘
                  │ HTTP
                  ▼
┌──────────────────────────────────────┐
│          Presentation Layer           │
│                                      │
│        TradeController               │
└─────────────────┬────────────────────┘
                  │
                  ▼
┌──────────────────────────────────────┐
│          Application Layer            │
│                                      │
│        TradeService                  │
└─────────────────┬────────────────────┘
                  │
                  ▼
┌──────────────────────────────────────┐
│            Domain Layer               │
│                                      │
│ PortfolioAllocationService           │
│ OrderCalculationService              │
│                                      │
│ Trade / Order / Stock / Portfolio    │
└─────────────────┬────────────────────┘
                  │
                  ▼
┌──────────────────────────────────────┐
│       Infrastructure Layer            │
│                                      │
│ PortfolioRepository                  │
│ StockRepository                      │
│ YAML Data Source                     │
└──────────────────────────────────────┘
```

### 設計方針

各レイヤーの責務を分離し、**ビジネスルールをPresentation LayerおよびInfrastructure Layerから独立**させる。

特に以下のロジックはControllerに実装しない。

* Portfolio Weight計算
* Weight Normalization
* Tradable判定
* Minimum Order Amount判定
* Quantity算出

# 3. コンポーネント設計

## 3.1 TradeController

### 責務

HTTP Requestを受領し、Application Serviceへ処理を委譲する。

### Interface

```text
POST /users/{userId}/trades
```

### 入力

```json
{
  "amount": 10000
}
```

### 処理

```text
HTTP Request
    ↓
Request Validation
    ↓
TradeService.createTrade()
    ↓
Response DTO生成
    ↓
HTTP Response
```

Controller自身は業務計算を実施しない。

---

# 4. TradeService

## 4.1 責務

Trade生成ユースケース全体をオーケストレーションする。

### Interface

```text
createTrade(userId, amount)
```

### 処理概要

```text
1. Trade Amount検証
2. Target Portfolio取得
3. Stock情報取得
4. Order Allocation実行
5. Order生成
6. Trade Response生成
```

---

# 5. PortfolioAllocationService

## 5.1 責務

Target Portfolioに基づく注文金額配分を担当する。

### Interface

```text
allocate(
    tradeAmount,
    targetPortfolio,
    stocks
)
```

### 処理

```text
Target Portfolio
       ↓
Stock Mapping
       ↓
Tradable Filter
       ↓
Valid Weight算出
       ↓
Weight Normalization
       ↓
Order Amount算出
       ↓
Minimum Order Amount Filter
       ↓
再Normalization
       ↓
最終Order Allocation
```

---

# 6. OrderCalculationService

## 6.1 責務

Order AmountおよびStock Priceから注文数量を算出する。

### Interface

```text
calculateQuantity(orderAmount, price)
```

### 数量算出

```text
quantity =
floor(orderAmount / price × 1000) / 1000
```

### 制約

```text
quantity × price <= orderAmount
```

を必ず満たす。

# 12. Order Allocationアルゴリズム

## Step 1：Trade Amount Validation

```text
amount < 1000
```

の場合は処理中断。

---

## Step 2：Target Portfolio取得

例：

```text
A = 31
B = 40
E = 29
```

---

## Step 3：Stock情報Mapping

```text
A → price=1000, tradable=true
B → price=155,  tradable=true
E → price=888,  tradable=false
```

---

## Step 4：Tradable Filter

```text
E → excluded
```

残存：

```text
A = 31
B = 40
```

---

## Step 5：Weight Normalization

```text
totalWeight = 31 + 40 = 71
```

```text
A = 31 / 71
B = 40 / 71
```

---

## Step 6：Order Amount算出

```text
A = floor(10000 × 31 / 71)
  = 4366

B = floor(10000 × 40 / 71)
  = 5633
```

---

## Step 7：Minimum Order Amount Filter

```text
amount < 200
```

のOrderを除外する。

---

## Step 8：再Normalization

除外対象が存在した場合、残存銘柄を対象としてWeightを再計算する。

---

## Step 9：Quantity Calculation

```text
quantity =
floor(
    amount / price × 1000
) / 1000
```

# 13. User 4の処理例

Input：

```text
Trade = 10,000円

B = 50%
C = 49%
D = 1%
```

初回配分：

```text
B = 5,000円
C = 4,900円
D = 100円
```

Dは、

```text
100 < 200
```

なので除外。

残存Weight：

```text
B = 50
C = 49
```

Normalization：

```text
B = 50 / 99
C = 49 / 99
```

再配分：

```text
B = 5,050円
C = 4,949円
```

Quantity：

```text
B = floor(5050 / 155 × 1000) / 1000
  = 32.580

C = floor(4949 / 2222 × 1000) / 1000
  = 2.226
```

# 16. 依存関係設計

依存方向は以下とする。

```text
Controller
    ↓
Application Service
    ↓
Domain Service
    ↓
Repository Interface
    ↓
Infrastructure
```

Domain Serviceから、

```text
HTTP
YAML
File System
Database
Framework
```

へ直接依存させない。

これにより、将来的に

```text
YAML
 ↓
DB
```

へデータソースを変更してもDomain Logicへの影響を最小化できる。

# 20. 実装時の重要設計判断

今回の課題では、特に以下を守るのが良いです。

### ① 金額と数量の責務を分離

```text
Allocation
    ↓
Order Amount

Order Calculation
    ↓
Quantity
```

を明確に分離する。

### ② 再配分処理を共通化

「Tradable=false」と「200円未満」は原因こそ異なるが、

```text
Order Candidate除外
        ↓
Weight再Normalization
```

という共通処理を持つ。

### ③ Controllerを薄くする

Controllerには、

```text
Request受領
↓
Service呼出
↓
Response返却
```

のみを持たせる。

### ④ Repositoryを抽象化する

現時点ではYAMLでも、

```text
PortfolioRepository
StockRepository
```

という抽象を設けておく。

将来的なDB移行に対する変更容易性を確保できる。

### ⑤ 金額計算の丸め規則を一箇所に集約

`floor`処理を各所に散在させず、**Money/Calculation UtilityまたはDomain Serviceに集約**する。
