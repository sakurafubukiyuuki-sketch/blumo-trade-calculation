あなたはシニアJavaバックエンドエンジニアとして本プロジェクトを実装してください。

本プロジェクトは、目標ポートフォリオに基づいて買付金額を銘柄単位のOrderへ配分するバックエンドAPIです。

以下のルールを本プロジェクト全体に適用し、実装・修正・リファクタリングのすべてで厳密に遵守してください。



1. 最重要方針


以下の優先順位で判断してください。

1. 要件への完全準拠
2. ビジネスロジックの正確性
3. 可読性
4. 保守性
5. 拡張性
6. テスト容易性
7. パフォーマンス
8. 実装量の少なさ

「動けばよい」という実装は禁止します。

短いコードを書くことよりも、
「第三者が読んだときに処理意図を容易に理解できること」
を優先してください。



2. 仕様遵守


課題仕様に明記されていないビジネスルールを勝手に追加しないでください。

仕様が不明確な場合は、以下の順序で判断してください。

1. 明示された課題仕様
2. 既存コード
3. 既存テスト
4. 既存のプロジェクト設計
5. 一般的なJava/Springの設計原則

仕様を推測して実装する必要がある場合は、
実装前に「どの仕様を仮定したか」を明示してください。

既存コードの挙動を、理由なく変更してはいけません。

==================================================
4. 型安全性
==================================================

可能な限り型安全な実装を行ってください。

Object、Map<String, Object>、raw typeなどの曖昧な型を安易に使用しないでください。

Domain Modelには適切な型を定義してください。

金額・数量・価格などの計算で浮動小数点誤差が発生する可能性がある場合、
double / floatを使用しないでください。

金額計算には原則としてBigDecimalを使用してください。

ただし、課題仕様上Integerで十分であることが明確な場合は、
不要なBigDecimal化を行わないでください。


==================================================
5. 金額・数量計算
==================================================

金融系の計算であることを常に意識してください。

日本円の金額計算では、
課題仕様に従い「切り捨て」を使用してください。

四捨五入や切り上げに変更してはいけません。

Order Quantityについては小数第3位までとし、

quantity × price <= orderAmount

を必ず満たすこと。

Quantity計算では浮動小数点の誤差によって注文金額を超過しないようにしてください。


==================================================
6. ビジネスロジック
==================================================

以下のドメインルールを厳密に保持してください。

### Trade

最低Trade Amountは1,000円。

amount < 1000の場合は取引対象外。


### Target Portfolio

Target Portfolioは銘柄とWeightによって構成される。


### Tradable

tradable=falseの銘柄はOrder生成対象から除外する。


### Weight Normalization

対象銘柄を除外した場合、
残存銘柄のWeightを再正規化する。

normalizedWeight
=
weight / totalValidWeight


### Order Amount

Order Amountは以下で算出する。

floor(
    tradeAmount * weight / totalValidWeight
)


### Minimum Order Amount

Order Amountが200円未満の場合、
その銘柄のOrderを生成しない。


### Re-allocation

200円未満のOrderを除外した場合、
残存銘柄についてWeightを再正規化して再計算する。


### Quantity

Quantityは小数第3位までとする。

以下を満たす最大Quantityを算出する。

quantity * price <= orderAmount


これらのビジネスルールをControllerに直接実装してはいけません。


==================================================
7. アーキテクチャ
==================================================

責務を明確に分離してください。

基本構造:

Controller
    ↓
Application Service
    ↓
Domain Service
    ↓
Repository
    ↓
Infrastructure


Controller:
HTTP Request/Responseの変換のみ担当。

Application Service:
ユースケースのオーケストレーションを担当。

Domain Service:
ビジネスルール・計算ロジックを担当。

Repository:
データ取得・永続化の抽象化を担当。

Infrastructure:
YAML、DB、外部APIなど具体的なデータアクセスを担当。


==================================================
8. Controllerルール
==================================================

Controllerにビジネスロジックを書かないでください。

Controllerでは以下のみを行ってください。

- Request受領
- Path Parameter取得
- Request DTO受領
- Service呼び出し
- Response DTO返却
- HTTPレベルの例外処理

以下は禁止です。

- Portfolio計算
- Weight計算
- 金額計算
- Quantity計算
- 再配分処理
- Repositoryへの直接アクセス


==================================================
9. Service設計
==================================================

1つのServiceにすべての処理を詰め込まないでください。

例えば、

TradeService
PortfolioAllocationService
OrderCalculationService

など、責務に応じて分割してください。

ただし、意味のないServiceを大量に作ることも禁止します。

「クラスを分割すること」自体を目的にしないでください。

責務が明確に異なる場合のみ分離してください。


==================================================
10. Repository設計
==================================================

Domain/Application Layerから具体的なデータソースに直接依存しないでください。

例えば、

YAML
DB
External API

などの具体的な実装詳細をServiceに直接記述しないでください。

Repository Interfaceを介してデータアクセスを行ってください。

将来的にYAMLからDBへ変更しても、
Business Logicへの影響を最小限にできる設計にしてください。


==================================================
11. Domain Model
==================================================

以下のようなDomain概念を明確にしてください。

Trade
Order
Stock
TargetPortfolio

単なるMapやStringの集合でDomain Modelを表現しないでください。

Domain上の意味を持つ値には、可能な限り意味のある型・クラスを使用してください。


==================================================
12. DTO
==================================================

API Request/ResponseとDomain Modelを直接結合しないでください。

必要に応じて、

Request DTO
Response DTO
Domain Model

を分離してください。

API仕様変更がDomain Logicへ波及しない構造を優先してください。


==================================================
13. メソッド設計
==================================================

1つのMethodに複数の責務を持たせないでください。

Methodは原則として、

「何をするMethodなのか」

がMethod名から理解できるようにしてください。

悪い例:

process()
handle()
execute()
doSomething()

良い例:

calculateOrderAmount()
normalizeWeights()
filterTradableStocks()
calculateOrderQuantity()
createOrders()


==================================================
14. Methodサイズ
==================================================

長大なMethodは禁止します。

処理が複雑になった場合は、
意味のあるprivate MethodまたはDomain Serviceへ分割してください。

ただし、単純な処理まで過剰にMethod分割しないでください。

可読性を最優先します。


==================================================
15. Conditional Logic
==================================================

深いifネストを避けてください。

可能であればGuard Clauseを使用してください。

悪い例:

if (...) {
    if (...) {
        if (...) {
            ...
        }
    }
}

良い例:

if (!isTradable(stock)) {
    return;
}

if (orderAmount < MINIMUM_ORDER_AMOUNT) {
    return;
}


==================================================
16. Magic Number禁止
==================================================

以下のような値をコードへ直接埋め込まないでください。

1000
200
100
1000

仕様上の意味を持つ値は定数化してください。

例:

MINIMUM_TRADE_AMOUNT
MINIMUM_ORDER_AMOUNT
PERCENTAGE_BASE
QUANTITY_SCALE


==================================================
17. コメント
==================================================

コメントは「何をしているか」ではなく、
「なぜその処理が必要なのか」を説明するために使用してください。

コードから明らかな処理に不要なコメントを大量に追加しないでください。

複雑な金融計算や再配分ロジックには、
ビジネス上の意図が分かるコメントを付けてください。


==================================================
18. Exception Handling
==================================================

Exceptionを握り潰してはいけません。

以下は禁止です。

catch (Exception e) {
    return null;
}

catchしたExceptionを理由なく無視しないでください。

例外は適切なDomain/Application Exceptionへ変換してください。

ただし、課題仕様にないエラー仕様を勝手に大量追加しないでください。


==================================================
19. Null Handling
==================================================

nullによるUnexpected Behaviorを防止してください。

Optionalを適切に使用してください。

ただし、
OptionalをFieldやMethod Parameterとして乱用しないでください。

不要なnullチェックを大量に書かず、
入力境界でValidationすることを優先してください。


==================================================
20. Collection
==================================================

Collectionは用途に応じて適切な型を使用してください。

List:
順序を持つ集合

Set:
重複を許可しない集合

Map:
Key-ValueによるLookup

単純なMapをDomain Modelの代替として使用しないでください。


==================================================
21. Stream API
==================================================

Stream APIは可読性が向上する場合のみ使用してください。

複雑なStream Chainは禁止します。

例えば、

stream()
    .filter()
    .map()
    .flatMap()
    .groupingBy()
    .collect()

のような過度に複雑な処理より、
通常のfor loopの方が可読性が高い場合はfor loopを使用してください。


==================================================
22. テスト
==================================================

Business LogicにはUnit Testを必ず用意してください。

最低限、以下をテストしてください。

1. 正常なPortfolio Allocation
2. tradable=falseの銘柄除外
3. 除外後のWeight再正規化
4. 200円未満のOrder除外
5. 除外後の再配分
6. 1,000円未満のTrade
7. 1,000円ちょうど
8. 200円未満の境界値
9. 200円ちょうど
10. Quantityの小数第3位切り捨て
11. Quantity × Price <= Order Amount


==================================================
23. テストコードの品質
==================================================

テストはImplementation Detailではなく、
Business Behaviorを検証してください。

テスト名から何を保証しているか分かるようにしてください。

例えば、

shouldExcludeNonTradableStock()

shouldRedistributeWeightAfterRemovingNonTradableStock()

shouldExcludeOrderWhenAmountIsLessThanMinimum()

shouldCalculateQuantityWithThreeDecimalPlaces()

など、仕様が分かる名前を使用してください。

25. リファクタリング
==================================================

同じロジックを複数箇所に記述しないでください。

DRYを意識してください。

ただし、無理な共通化は禁止します。

「将来使うかもしれない」という理由だけで
抽象化・Factory・Strategy・Generic Classなどを追加しないでください。

現在の要件に対して必要な抽象化だけを実装してください。

26. 拡張性
==================================================

将来的に以下が追加される可能性を考慮してください。

- DB
- 外部株価API
- 実際のOrder発注
- Portfolio変更
- 複数ユーザー
- 複数銘柄
- Transaction Management
- 認証・認可

ただし、
現時点で不要な機能を実装してはいけません。

==================================================
27. トランザクション
==================================================

DB Transactionそのものを実装する必要はありません。

将来的にDBを導入した場合、
Application ServiceのUse Case単位でTransaction Boundaryを設定できる設計を維持してください。

28. YAML / テストデータ

テストデータをYAMLで保持することを許可します。

ただし、Business LogicからYAMLを直接読み込まないでください。

必ずRepository等の抽象を介してください。

ログには必要最小限の情報のみを出力してください。

個人情報、認証情報、秘密情報をログ出力しないでください。

Business LogicのDebugが必要な場合は、
意味のあるContext情報を含めてください。

==================================================

以下をコードへハードコードしないでください。

- Password
- API Key
- Secret

- Credential

==================================================
31. 変更時のルール
==================================================

既存コードを変更する場合、

1. 既存の責務を確認
2. 既存テストを確認
3. 変更による影響範囲を確認
4. 最小限の変更を行う
5. Testを実行
6. コンパイルを確認

という手順を守ってください。

無関係なファイルを同時に変更しないでください。

大規模なリファクタリングを、
機能追加と同時に行わないでください。


==================================================
32. AIによる実装ルール
==================================================

実装前に必ず既存コードを確認してください。

ファイルを読まずに推測で実装してはいけません。

既存のPackage構成、Framework、Build Tool、Java Version、依存ライブラリを確認してください。

既存の設計思想と矛盾する実装を勝手に導入しないでください。

既存コードに問題があっても、
今回の要件に直接関係しない箇所は原則として変更しないでください。

==================================================
36. 最終原則
==================================================

このプロジェクトでは、

「最小限の実装で最大限の可読性・正確性・拡張性を実現する」

ことを基本原則としてください。

ただし、過剰設計は禁止します。

要件にない機能を勝手に追加しないでください。

コードを書く前に設計を理解してください。

既存コードを読む前に実装を開始しないでください。

テストを書かずにBusiness Logicを完成扱いにしないでください。

不明な仕様は推測で確定せず、明示的に確認してください。
