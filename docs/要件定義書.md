# 要件定義書

**文書種別：** 要件定義書
**対象システム：** 目標ポートフォリオ連動型買付注文計算API
**対象機能：** Trade登録・Order生成
**API起動ポート：** `1111`
**データストア：** 現時点ではDB非依存
**作成目的：** ブルーモ型投資アプリケーションにおける買付注文生成ロジックのPoC実装

---

# 1. システム概要

## 1.1 システム目的

顧客が指定した買付金額を、顧客ごとに設定された目標ポートフォリオ（Target Portfolio）に基づいて銘柄単位の注文（Order）へ分解し、各銘柄の取引可否、最低注文金額および市場価格を考慮した買付注文情報を生成する。

本機能は、将来的なバックエンドシステム拡張を前提とした**ビジネスロジックの基盤コンポーネント**として実装する。

---

# 2. 用語定義

| 用語        | 英語               | 定義                      |
| --------- | ---------------- | ----------------------- |
| 目標ポートフォリオ | Target Portfolio | 顧客が保有を希望する銘柄および各銘柄の構成比率 |
| 取引        | Trade            | 顧客からシステムへ送信される買付依頼単位    |
| 注文        | Order            | Tradeを銘柄単位に分解した発注単位     |
| 銘柄        | Stock / Security | 売買対象となる金融商品             |
| 取引可能フラグ   | Tradable         | 当該銘柄が注文対象として利用可能かを示す属性  |
| 注文金額      | Order Amount     | 各銘柄に割り当てられた日本円金額        |
| 注文数量      | Quantity         | 当該銘柄について発注する数量          |

---

# 3. 業務要件

## BR-001 買付依頼受付

顧客は買付金額を指定して買付依頼を実行できること。

## BR-002 Target Portfolioに基づく資金配分

システムは、対象顧客のTarget Portfolioを取得し、買付金額を各銘柄の構成比率に基づいて配分すること。

## BR-003 取引不能銘柄の除外

Target Portfolioに含まれる銘柄が `tradable = false` の場合、当該銘柄をOrder生成対象から除外すること。

## BR-004 構成比率の再正規化

取引不能銘柄を除外した場合、残存銘柄の構成比率を再正規化し、Trade Amountを再配分すること。

# 4. 機能要件

## FR-001 Trade受付API

システムは以下のREST APIを提供すること。

 Request Parameter

| 項目      | 型              | 必須 | 説明    |
| ------- | -------------- | -- | ----- |
| user_id | Integer/String | ○  | 顧客識別子 |
| amount  | Integer        | ○  | 買付金額  |

---

## FR-002 Target Portfolio取得

`user_id`をキーとしてTarget Portfolioを取得すること。

## FR-003 銘柄マスタ取得

Order生成に必要な以下の属性を取得すること。

取得対象：

* ticker
* price
* tradable

## FR-004 Order Amount算出

有効銘柄についてTarget PortfolioのWeightに基づきOrder Amountを算出すること。

算出式：

```text
Order Amount
= floor(
    Trade Amount × Weight / Total Valid Weight
  )
```

日本円の金額計算結果は切り捨てとする。

## FR-005 最低Order Amount判定

算出されたOrder Amountが200円未満の場合、当該Orderを生成しないこと。

## FR-006 除外後の再配分

FR-005によりOrder生成対象外となった銘柄が存在する場合、当該銘柄を除外した上で残存銘柄に対してWeightを再正規化すること。

処理は必要に応じて再実行可能な設計とする。


## FR-007 Order Quantity算出

各Orderについて、銘柄価格に基づき注文数量を算出すること。
数量は小数点以下3桁までとする。


## FR-008 Order金額超過防止

生成されるQuantityについて、
Quantity × Stock Price <= Order Amount
を必ず満たすこと。

したがってQuantityの算出時には切り捨て処理を適用する。

## FR-009 Response生成

処理結果として以下の情報を返却すること。

```json
{
  "amount": 10000,
  "target_portfolio": {
    "A": 40,
    "B": 60
  },
  "orders": [
    {
      "symbol": "A",
      "amount": 4000,
      "quantity": 4.0
    },
    {
      "symbol": "B",
      "amount": 6000,
      "quantity": 38.709
    }
  ]
}
```

# 5. ビジネスルール

## BR-001 最低Trade Amount

1,000円未満のTradeは受付対象外とする。

## BR-002 日本円端数処理

日本円金額については全て切り捨て（Floor）を適用する。

四捨五入および切り上げは使用しない。

## BR-003 最低Order Amount

200円未満のOrderは生成しない。


## BR-004 Tradable判定

tradable = true
の銘柄のみOrder生成対象とする。


## BR-005 Weight再正規化

Order生成対象外となった銘柄のWeightは配分計算から除外し、残存銘柄のWeight合計を基準として再正規化する。


## BR-006 Quantity精度

Quantityは小数点以下3桁までとする。

# 6. データ要件

## 6.1 Stock

| 項目       | 型       | 必須 | 説明    |
| -------- | ------- | -- | ----- |
| ticker   | String  | ○  | 銘柄コード |
| price    | Decimal | ○  | 現在価格  |
| tradable | Boolean | ○  | 取引可否  |

```yaml
  price: 2222
  tradable: true

  price: 467
  tradable: true

  price: 888
  tradable: false
```

# 7. 処理フロー

```text
[HTTP Request]
      │
      ▼
TradeController
      │
      ▼
TradeService
      │
      ├── Target Portfolio取得
      │
      ├── Stock情報取得
      │
      ▼
有効銘柄抽出
      │
      ├── tradable = false → 除外
      │
      ▼
Weight正規化
      │
      ▼
Order Amount算出
      │
      ├── < 200円 → 除外
      │
      ▼
Weight再正規化
      │
      ▼
Order Amount再算出
      │
      ▼
Quantity算出
      │
      ▼
Order生成
      │
      ▼
TradeResponse
```

# 8. エラー要件

仕様上明示されていないものについては、実装時に既存コード・テスト仕様と整合させる。

最低限、以下を考慮する。

| ケース                 | 処理                 |
| ------------------- | ------------------ |
| amount < 1,000      | Validation Error   |
| user_id不正           | Resource Not Found |
| Target Portfolio不存在 | Resource Not Found |
| 全銘柄tradable=false   | orders=[]          |
| Order Amount < 200  | Order対象外           |
| Stock Price <= 0    | データ不整合として扱う    |

HTTP Statusについては、既存プロジェクトのエラーハンドリング規約がある場合、それに準拠する。

# 9. 非機能要件

## NFR-001 起動要件

アプリケーションは以下で起動可能であること。

localhost:1111


## NFR-002 可用性

本課題では可用性要件を設定しない。

ただし、将来的な高可用性化を阻害しない設計とする。


## NFR-003 データベース

現時点ではDBを必須としない。

テストデータはYAML等の設定ファイルによる保持を許容する。

ただし、将来的なDB導入を考慮し、Domain/Application LogicとData Access Layerを疎結合にする。

## NFR-004 保守性

ビジネスルールとインフラストラクチャ層を分離し、変更影響範囲を局所化すること。

特に以下をControllerに実装しない。

* Weight計算
* 再正規化
* 最低注文金額判定
* Quantity計算


## NFR-005 拡張性

将来的に以下の変更が発生することを想定する。

* DB導入
* 銘柄数増加
* Portfolio管理機能追加
* Order発注処理追加
* 外部市場データ連携
* トランザクション管理

そのため、Business Logicを独立したApplication/Domain Serviceとして実装可能な構造とする。

---

## NFR-006 テスト容易性

ビジネスロジックは副作用を可能な限り排除し、Unit Testによって個別検証可能な構造とする。

Eのみ存在し、tradable=false

Eを除外。

quantity * price <= amount

をassertする。


# 11. 設計上の責務分割

Controller
  └─ HTTP I/Oのみ

Application Service
  └─ Trade Use Case orchestration

Domain Service
  ├─ Portfolio Allocation
  ├─ Weight Normalization
  └─ Order Quantity Calculation

Repository
  ├─ Portfolio取得
  └─ Stock取得

Domain Model
  ├─ Trade
  ├─ Order
  ├─ Stock
  └─ TargetPortfolio

特に、

> Controller → Service → Repository

という依存方向を維持し、Domain LogicがHTTPやYAMLの実装詳細に依存しない構造が望ましいです。
